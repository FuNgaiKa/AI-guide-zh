# 后端开发该怎么选 AI 模型：Luna、Sol 与 Astra 的真实分工

> 最后更新：2026-09-14
>
> 适用范围：后端开发中的工单处理、问题排查、技术方案、代码实现与测试。

> **最新体验追加（2026-09-22）：** 当前日常主力已经调整为 **Sol Medium**，复杂问题的设计与复核使用 **Astra Low**。下文原有结论与 2026-09-14 的体验继续保留，作为使用方式变化的历史记录；当前选择以 2026-09-22 的新增内容为准。

## 先说结论

我的分工逻辑是：

- **Luna Max Fast 作为日常主力**，处理高量、重复性和目标明确的任务。
- **Sol High 更适合明确的复杂工程开发**。额度充足时，可以作为日常 driver 和实现工程师。
- **Astra Medium 作为高价值升级**，负责方案、机制、架构和 Skill 设计。

如果打个比方，Sol 像一个很强悍的工程师，Astra 像一个非常聪明的设计师。具体怎么选，还要结合任务类型、等待时间和额度预算；这份结论是个人工作流总结，不代表所有项目都会得到相同结果。

## 先说明 Luna Max 和 Luna Max Fast

本文有意保留两种写法：

- **日常体验与建议中的 Luna Max Fast**，指我实际使用的 Codex 档位。
- **公开评测中的 Luna Max**，指 DeepSWE 原始数据里的 `gpt-5-6-luna / max` 配置。

DeepSWE 没有单独记录 Fast 模式，因此不能把榜单耗时当成 Luna Max Fast 的严格测速。下文只在使用体验中讨论 Fast；引用评测时统一写 Luna Max。

## 模型定位快速对比

以下官方定位和 API 标准文本 token 价格核对于 **2026-09-14**。API 价格不等于 ChatGPT 或 Codex 产品内的额度消耗；额度相关描述均为个人使用体感。

| 维度 | GPT-5.6 Luna | GPT-5.6 Sol | GPT-6 Astra |
| --- | --- | --- | --- |
| 官方定位 | 面向成本敏感、高吞吐工作负载 | 面向复杂专业工作的旗舰模型 | 面向最困难端到端工作的最强模型 |
| API 价格（输入 / 输出，每百万 tokens） | \$0.20 / \$1.20 | \$4 / \$20 | \$10 / \$50 |
| 我的定位 | 高性价比干活档，负责日常吞吐 | 强悍的工程师，负责明确而复杂的实现 | 聪明的设计师，负责判断、取舍和高风险决策 |
| 适合任务 | 明确任务、常规实现、测试、文档、常规排查 | 大仓库 Bug、跨服务重构、硬核长程任务 | 复杂根因分析、架构方案、多系统联调、高风险决策 |
| 主要取舍 | 省额度；Max 档等待更久，开放问题需要更多引导 | 复杂工程任务更稳，但额度消耗高出不少 | 判断力更强、返工更少，但额度消耗明显更快 |

## 持续更新的使用体验

后续体验按日期追加并保留历史判断，方便观察模型、任务和个人使用方式发生变化后，结论是否改变。

### 2026-09-22：主力收敛为 Sol Medium + Astra Low

和朋友一起使用 Pro 5× 后，我的日常组合逐渐收敛为 **Sol Medium 与 Astra Low**。平时主要在工作日使用，任务集中在工单查询、代码设计、代码实现和 Bug 修复。

#### Sol Medium：不开 Fast 也足够覆盖日常开发

目前绝大多数任务都直接使用 Sol Medium。在不开 Fast 模式的情况下，它的完成速度和结果已经能够满足日常需要：工单信息整理、日志与代码查询、常规方案设计、代码实现、测试补充和 Bug 修复，基本不需要为了速度额外开启 Fast。

与上一阶段使用 Luna Max Fast 或 Sol High 相比，现在更倾向于固定使用 Sol Medium，而不是频繁切换模型和推理强度。对需求相对明确、能够通过代码和测试验证的工程任务，Medium 已经比较够用。

#### Astra Low：用于复杂问题的设计与复核

Astra Low 主要用于少量但更依赖判断力的任务，例如复杂问题拆解、根因不明确的排查、架构与机制设计、多系统之间的边界梳理，以及高风险改动的最终复核。

这里选择 Low 而不是更高推理强度，是因为当前需求主要是借助 Astra 的理解、判断和取舍能力，并不一定需要它在每个任务上进行很长时间的探索。先用 Astra Low 把方向和约束想清楚，再交给 Sol Medium 实现，是目前更符合实际使用量的组合。

#### 三人使用 Pro 5× 的额度体感

在三人协作、主要于工作日使用的情况下，以 Sol Medium 为主、偶尔使用 Astra Low，每个工作日的用量大约可以控制在额度面板的 **20% 左右**。

这个数字只是当前人员数量、任务类型和使用习惯下的实际观察，不是官方额度承诺，也不能直接推导出其他团队的可用量。长程任务数量、上下文长度、工具调用、是否开启 Fast，以及 Astra 的使用频率，都会影响实际消耗。

#### 当前任务分工

| 任务 | 当前选择 |
| --- | --- |
| 工单查询、信息整理、日志与代码检索 | Sol Medium |
| 常规代码设计、代码实现和测试补充 | Sol Medium |
| 明确问题的 Bug 修复与回归验证 | Sol Medium |
| 复杂问题拆解与根因分析 | Astra Low |
| 架构、机制和跨系统边界设计 | Astra Low |
| 高风险改动的方案与最终复核 | Astra Low |

目前默认使用 Sol Medium；当任务的核心从“把明确的事情实现出来”变成“判断方向是否正确、边界是否完整、风险是否可接受”时，再切换到 Astra Low。

### 2026-09-14

#### Luna Max：省额度，但等待时间更长

我体感它在三个常用档位中完成任务最慢，长任务中更容易遇到上下文压缩。简单需求、不着急的任务，用它仍然很合适。这段体验也让我更在意高推理强度带来的等待时间，而不只是效果和额度。

Luna Max Fast 在我的工作流里属于“高性价比干活档”。日常高量后端工作依然很合适，真正困难的长程 agent 任务则建议升级到 Sol 或 Astra。

#### Sol High：更适合明确的工程开发

相比 Luna Max，我体感它完成任务更快，处理复杂问题更稳；同一次上下文中往往能推进更多工作，压缩没有那么频繁，任务状态也保持得更好。不过，额度消耗高出不少。

这些现象不能直接归因于推理长短，任务本身、工具输出和上下文使用方式同样会影响体验。

只要需求明确，并且有比较完善的测试和验收机制，即使是复杂系统开发，我也会优先考虑 Sol High。它像一个很强悍的工程师，适合先把具体事情做出来，再根据验证结果不断修正。

#### Astra Medium：更适合依赖判断力的设计工作

方案、机制、架构和 Skill 设计，很难仅靠测试通过来保证质量。我体感 Astra 更容易理解意图、抓住重点并做出取舍，表达也更精炼；在这些任务里，完成速度比另外两个常用档位更快，结果也更合心意。我愿意直接用它，争取尽可能少地返工。

它的额度消耗也明显更快，但少量设计工作通常是人与 AI 一起思考的过程：AI 输出后，人要阅读、判断、讨论，再继续推进，总用量不一定很大。这时我更愿意把额度花在更强的判断力上。

## 三个常用档位的公开评测

为了避免把不同评测、不同 agent harness 和不同推理档位硬拼在一起，这里只采用 **DeepSWE v1.1** 横向比较。该基准包含 113 个原创的长周期软件工程任务，所有模型统一使用 mini-swe-agent。

数据读取于 **2026-09-14**。下表由 [DeepSWE v1.1 原始 trials 数据](https://deepswe.datacurve.ai/artifacts/v1.1/trials.json)计算得出，筛选条件为：

- `eval_scope=full`
- `source=deep-swe`
- `included_in_score=true`
- 模型配置分别为 `gpt-5-6-luna / max`、`gpt-5-6-sol / high`、`gpt-6-astra / medium`

| 档位 | DeepSWE v1.1 通过率 | 平均完成时间 | 平均输出 tokens | 平均 agent 步数 |
| --- | ---: | ---: | ---: | ---: |
| **Luna Max** | **67.2%** | 18.7 分钟 | 73.4K | 101.7 |
| **Sol High** | **69.4%** | **9.9 分钟** | 28.5K | 36.9 |
| **Astra Medium** | **72.8%** | 14.7 分钟 | **20.4K** | **26.0** |

这些结果是对入选 trials 的聚合，不是只跑一次得到的单点成绩。Luna Max、Sol High 和 Astra Medium 分别汇总了 448、451 和 452 条入选记录，覆盖同一组 113 个任务。通过率与平均值由原始数据重新计算；页面展示的置信区间和后续变更请以 [DeepSWE v1.1 排行榜](https://deepswe.datacurve.ai/)为准。

### 这张表怎么理解

- **Luna Max 仍然能完成大多数长周期代码任务，但过程更长。** 在这组数据中，它的平均用时、输出 token 和 agent 步数都是三者中最高的。这和我实际使用时“能做，但等待更久、长任务更容易遇到压缩”的体感方向一致。
- **Sol High 是三者中完成任务最快的档位。** 相比 Luna Max，它的通过率高 2.2 个百分点，平均完成时间缩短约 47%，输出 token 减少约 61%。这支持把它作为需求明确、有测试和验收机制时的工程实现主力。
- **Astra Medium 的通过率最高，过程也最精简。** 相比 Sol High，它的通过率高 3.4 个百分点，输出 token 减少约 28%，agent 步数减少约 29%；但平均完成时间长约 49%。它在这项评测中不是最快的，却用更少步骤取得了更高的点估计得分。
- **几分的差距不能机械解释为绝对能力差距。** DeepSWE 的相邻配置存在置信区间重叠，而且单一代码基准无法衡量架构取舍、表达质量和 Skill 设计。Astra 更适合设计工作的判断，主要仍来自实际体验，而不是这张表单独证明的。

因此，只看这项公开评测：

- 看额度和日常吞吐，Luna Max 是低成本主力。
- 看明确工程任务的完成速度，Sol High 是三者中更平衡的选择。
- 看复杂任务的通过率和执行过程精简程度，Astra Medium 的结果最好，但不代表它在所有任务中都最快。

## 推荐分工：放进后端开发工作流

### 1. 日常工单与常规问题排查

- 现象清晰、日志或错误信息相对明确：优先 Luna Max Fast。
- 跨多个服务、历史债务重、日志不全、需要深度假设验证：升级到 Astra Medium。
- 问题明确但实现链路很长，需要在仓库中持续推进：考虑 Sol High。

### 2. 编写需求技术方案

- 初稿或常规方案：用 Luna Max Fast 快速产出结构、接口、数据流和风险点。
- 重要、复杂或高风险方案：用 Astra Medium，尤其是性能瓶颈、分布式一致性、高并发、安全边界和长期演进问题。
- 方案已经明确，需要把它细化为可执行的工程步骤：可以交给 Sol High。

### 3. 代码开发

- 日常 CRUD、接口实现、普通重构、工具类、单元测试补全：Luna Max Fast。
- 大仓库复杂 Bug、跨服务重构、需要长时间自主推进：Sol High。
- 核心逻辑、复杂状态机、并发控制、性能敏感路径或高风险遗留代码改造：Astra Medium 先做判断与设计，再决定由谁实现。

### 4. 代码测试

- 单元测试、集成测试用例、mock 和常规边界用例：Luna Max Fast。
- 已有验收目标、需要持续修复和回归：Sol High。
- 分布式一致性验证、性能压测或混沌测试策略：Astra Medium 先设计测试方案。

## 实用切换原则

默认用 Luna Max Fast；满足以下任一条件时考虑升级：

- 问题已经排查 30–60 分钟，仍没有明确方向。
- 涉及架构级决策或长期技术债。
- 失败成本高，例如生产事故、数据一致性或安全问题。
- 需要模型主动进行多步骤探索，而不是由人一步步引导。
- 自己对当前方案没有足够信心。

成本控制可以遵循四条原则：

1. 先让 Luna 快速尝试 1–2 轮，失败或质量不足再升级。
2. 给 Astra 更完整的上下文和明确目标，减少无效探索。
3. Luna 不必每个任务都开 Max；明确的小修复可先用较低推理档位。
4. 不要让 Astra 只交付一份“漂亮方案”，还应明确文件、改动点、验收标准和风险。

## 一套可执行的工作流

1. **Astra Medium** 理解需求、拆解方案、识别风险和边界。
2. **Luna Max Fast** 按方案修改代码、运行测试、处理机械性迭代。
3. 任务明确但实现复杂、需要更强的长程执行时，由 **Sol High** 担任 driver。
4. 遇到架构分歧、连续测试失败或高风险改动，再切回 **Astra Medium** 复核。

如果只在 Luna 和 Astra 之间分工，我目前会让 Luna Max Fast 覆盖约 70%–85% 的日常工作量，让 Astra 负责其余真正困难、高风险或高价值的部分。这个比例只是个人经验估计，不是评测数据。

一句话总结：**让 Astra 做架构师，让 Luna 做高效率工程师，再让 Astra 做最终 code review；Sol 额度充足时，则可以成为复杂工程实现的日常 driver。**
